# AI芯片动态调度与数据流架构 完整深度总结（含大模型超节点演进趋势）

## 一、核心定性：动态调度与数据流并非对立，而是一体两面

这是本次讨论最核心的底层认知，破除行业常见误区：

**动态调度是上位概念**：运行时根据依赖是否满足、资源是否空闲，决定何时发射。数据流并不是它的反面，而是其中一类——**带编译期约束的受限动态调度**。

1. **广义动态调度（常以乱序执行为代表）**

乱序执行是动态调度在 CPU 指令流水线中的经典实现：编译器只输出线性指令流，**不固定计算拓扑、不做资源绑定**；硬件靠重命名、记分牌、乱序窗口处理未知依赖、分支与不规则访存。

优势是**极致通用**；代价是调度逻辑面积、功耗、延迟高，大量晶体管花在「怎么发」而非「怎么算」。

2. **AI 数据流（受限动态调度）**

数据流**没有抛弃动态调度**，而是**编译期定骨架、运行时轻量触发**：

- 编译期：固化拓扑、通路、PE 映射；
- 运行时：在固定骨架内做就绪触发、负载均衡、消气泡。

其内部并不统一：有的几乎排死时间表，有的保留更明显的令牌就绪；共同点是**强编译约束**，差别只在运行时还能机动多少。

3. **一体两面**

> 数据流 = 静态编译框架 + 受限动态调度  
> 乱序一类 = 弱拓扑约束 + 高自由度、高开销动态调度

场景化取舍，不是绝对对错：数据流用软件复杂度换算力密度与能效；广义乱序用硬件开销换通用性。用 CPU 全乱序的标准否定数据流，是用错了评价尺。

两者既要「会调度」，就都碰到同一道门槛：**调度器一次能看见、能挖的有效计算图有多大**——窗口与图的匹配，是下一章的主题。

## 二、调度窗口与计算图：太小、太大，与合适大小

调度窗口这里指：一次能处于「可调度 / 在途」的**指令或 op（图节点）**范围（不是 shared mem / 显存那类存储上限）。窗口深度多半藏在微架构或编译器内部，开发者不易直接看见。

核心不是「越小越好 / 越大越好」，而是：**有效图要落在窗口能吃饱、又不迫使软硬件扛不住的区间**。下面分太小、太大，再收束到「合适」。

### 1. 图太小：并发度不够

业界常见路径是细粒度小算子 launch / 逐算子提交。核内仍可动态调度，但**跨算子**并行与流水不足——尤其依赖链被切开时，边界气泡大；无依赖多核用多 Stream 重叠，往往还不是主痛点。

数据流路线通常靠编译器把子图做大再映射，较少停留在 eager 小图 launch。放大有效域的手段彼此**互补，而非单选**：

| 手段 | 作用 | 局限 |
|---|---|---|
| **融合 / 子图放大** | 多 op 进入同一调度域，治本 | 实现难；域变大后可能反过来超窗 |
| **CUDA Graphs 等** | 一次提交多节点，利于无依赖重叠 | 不等于更大的 op 级调度窗 |
| **PDL 等依赖核重叠** | 压依赖边界气泡、提高 prefetch 效率 | 治标；域仍碎；有硬件代数边界 |

### 2. 图太大：编译可得，窗口会超

整图或近整图由编译器生成**可行**，难在复杂与维护（时间、依赖分析、动态 shape、增量更新等），不是「做不到」。真正顶住的是：若要求海量 op **同时**待在调度窗口里，就绪与在途状态会胀。

超窗之后，常见处理（可组合）大致是：

| 手段 | 做法 | 要点 |
|---|---|---|
| **一次装得下就装** | 融合域 op 数 ≤ 窗口 | 最省事；域够小时成立 |
| **编译器静态切块 / 换配置** | 按内部窗口预算切开，块间同步再装下一块 | AI 加速器上很常见；切在软件；若需换 PE 映射，比插一条 sync 重 |
| **同流内插屏障分期** | 一次 launch 的长流里插 sync，排空后再进下一批 | **不必重新 launch**；跨屏障无法再一起动态调度。多为编译期插好，而非硬件运行时自动检测超窗 |
| **滑动窗口** | 完成则后滑、新 op 连续准入 | CPU 乱序的经典伴随形态；以全图滑窗做 AI 主路径的较少，复杂度在运行时准入/发射 |

「插 sync 即可、不必再切再 launch」在**同构长流、不必重映射**时成立；要换空间配置时，仍更接近静态切块那一路。

### 3. 收束：需要合适大小的图

太小则调度挖不满；太大则要切块、屏障或滑窗，跨边界的并发与局部性都要付代价。工程目标是落到**窗口能吃饱、边界又可控**的有效图——往往靠融合做大，再按预算切开或分期。

于是问题递进为：**这张合适的图怎么构造、边界怎么切**——横向要并行，纵向要局部性。这是下一章。

## 三、核心工程权衡：计算图的横向并行 \& 纵向存储局部性切块策略

第二章收束到「要有合适大小的图」之后，若走切块或分期，接下来才是**边界怎么画**：不能只看数据依赖，必须在并行收益和访存损失之间权衡。

1. **横向划分（并行维度）**

优先将**无数据依赖、可并行执行**的算子聚合为同一BB子图块，最大化块内动态调度的乱序并发能力，充分释放硬件并行算力。

这里要和「外层并发」分开：编译器识别无依赖后走多 Stream / CUDA Graphs 等，也能重叠执行，但那是**软件/运行时粗粒度调度**；窗内动态调度的低延迟发射，只作用于**窗口里可见的指令/op**。横向打包的目的，不只是「能并行」，更是**把可并行工作喂进窗口**。外层并发不能替代喂窗；当然也不是所有并行都必须挤进同一窗——超窗或资源压力时仍要外层手段——但若要吃到动态调度本身的红利，就必须进窗。

2. **纵向划分（快存局部性维度）**

不能单纯拆分串行依赖算子：**存在链式数据依赖、共享片上SRAM/快存**的串行算子，必须保留在同块或相邻块。

- 错误做法：仅按“无依赖打包”，拆分串行链式算子；

- 致命后果：中间结果无法驻留片上快存，被迫下刷DDR慢内存，带来毁灭性访存延迟与带宽损失。

> 最终切块原则：**并行挖掘优先，存储局部性兜底**，在调度并发收益和访存开销之间取平衡。memory-bound 场景下，局部性往往还要排得更前。

边界有了大致原则之后，还要问：**这样的块谁来构造**——手写大算子，还是编译器自动融合。这是下一章。

## 四、实现路径对比：手写算子大图 VS 编译器自动融合

第三章之后，问题变成：**合适大小、喂得进窗的块，谁来构造？** 两条路径目标一致——撑起有效调度域——而不是为融而融。

1. **手写大算子（人工构图）**

人工搭建大计算区域，把更多工作送进同一调度域，便于挖满动态调度，并在算法与访存结构上做到极致。

在动态调度下，手写的「把指令序排成 cycle 级时间表」红利会变弱：实际发射序由窗口按就绪决定，手排顺序不必等于执行顺序，手写门槛也因此略降。真正仍常拉开差距的，是算法与 tiling、显式多 stage / 双缓冲等存储与流水结构（硬约束仍在，调度只在约束内找机会）。短板是成本高、迭代慢、难覆盖海量模型；窗深或硬件一变，巨核往往要人肉重切，偏脆。

2. **编译器自动算子融合（编译构图）**

自动聚合小算子、生成子图，按内部窗口等预算做融合与切分，平衡并行与局部性，换代和超窗时更容易重来一遍。

短板是**软件复杂度高**（切分、映射、依赖、动态 shape 等）。指令级排序上与手写的差距易缩小；热点上的算法形态与极致流水，仍常落后专家核。

二者是**互补**：热点路径手写凿天花板，长尾与切分/换代靠编译器铺开。构图路径选定之后，更深一层是架构取舍——用多少软件复杂度，换多少硬件能效。这是下一章。

## 五、架构终极取舍：无银弹，软件换硬件算力上限

构图交给软件之后，更深一层的取舍是：**用多少软件复杂度，换硬件上的能效与算力密度上限**。

1. **数据流架构核心优势**

将复杂的拓扑编排、图优化、资源规划压入编译期，大幅简化硬件逻辑；

硬件不必堆昂贵的通用乱序、重命名、大窗口记分牌，**省下的晶体管更多用于计算单元与片上缓存**，同工艺下更容易把密度和能效打高。

2. **架构固有边界**

更适配**规整、可静态或半静态编译的 AI 负载**；面对随机分支、未知动态依赖、不规则计算，灵活性不如广义动态调度（乱序）来得自在。

3. **核心结论**

动态调度与数据流**没有绝对赢家**，是场景化工程取舍：

- 通用计算：高自由度乱序动态调度通常更合适；
- 规整张量类 AI 训练/推理：**强编译约束 + 受限运行时**通常更划算——落地表可以是经典数据流、SIMT + 融合编译、偏确定性时间表等，**形态不唯一**，不宜写成「只有数据流才是最优解」。

单芯片这条线，是从动态调度架构出发，依次问过「怎么调度、怎么喂图、谁来构图」，最后落到**按场景做软硬件分工**：软件扛多少复杂度、硬件留多少灵活与密度，以换取算力密度、能效，以及与之相关的片上带宽与吞吐。这些讨论回答的是——**单片上的软件如何设计、与硬件如何取舍，才能把单芯片能力打满**。

但业界趋势下，一套 AI 系统能否成立，不能只看单片，还要看**集群能否把单片能力组织起来**。过于盯住单片、忽略集群设计固然不妥；反过来，集群叙事里也仍要说清**单片能力在集群中扮演什么角色**——它是入场券，还是会被通信与存储稀释。下一章就此作开放讨论。

## 六、开放讨论：超节点时代的单片能力与集群能力

接上章：单片能力如何打满，已经谈过一轮；开放的问题是——**这些能力怎样被集群组织起来，又有多少能落到系统出口**。

### 1. 集群在难什么

超节点与大规模训练/推理里，卡点**常常**不在「某一颗芯片算没算满」，而在：

- 多级存储（KV Cache、权重与激活的分层驻留）；
- 片间 / 节点间带宽与集合通信延迟；
- 张量、流水、专家等并行下的负载均衡与气泡。

单片利用率很高，仍可能被跨卡等待、缓存放不下、通信不同步拖住。说「系统层变重」是准确的；说「片内优化从此无意义」则过满。

### 2. 单片能力在集群里扮演什么

集群会反向切割单片软件：TP/PP/EP 与通信插入，往往把精心融合、切块的调度域打碎，窗内动态调度的红利在出口上被稀释。这是「单片最优 ≠ 系统最优」。

但单片并非退场，角色更宜拆开看：

- **入场券**：算力密度、能效、片上带宽与单卡效率，仍划出成本与时延的下限（推理尤其敏感）；
- **可被组织的硬件能力**：HBM、片间互联、同步与集合通信原语等，本身就是集群能力的底座，不是「纯软件 Infra」能够凭空替代；
- **易被稀释的部分**：仅优化窗内发射、局部融合，而上层切图与通信很粗时，系统出口上可能看不见。

因此不宜写成「Infra 高于微架构」的单极；更像是**层与层之间的接口问题**——编译与并行策略如何少打碎局部性，硬件暴露何种同步与带宽，才让集群吃得到单片。

### 3. 产业把「域」做大，说明了什么

近两年超节点叙事，高水平上相当一致：**尽量做大 Scale-up 域，再在域间 Scale-out**。例如华为开放面向超节点的互联协议灵衢（UnifiedBus），强调总线级互联、协议归一与池化等，使多机在逻辑上更像一台；平头哥真武系列配合 ICN 等互联做超节点，突出统一内存编址 / 内存语义与域内高带宽低时延，再经网络扩到更大规模集群。这些并不取消单片，而是把「有效执行域」从单芯片延伸到紧耦合多卡——与前文「域太碎则调度与流水吃亏」是同一类问题，只是抬到了机柜与集群。

### 4. 开放收束

单片打满是**必要基础**；通信、存储与分布式 Infra 往往决定**集群出口上限**；二者未脱钩。竞争舞台变大了，不是把下一层关掉。

仍值得继续追问的，是层间接口：并行切割下如何保住局部性与有效域？硬件与协议如何让「多卡像一域」付得起代价？——此处只标出问题，不作终局答案。

## 全文终极总结

1. 动态调度与数据流一体两面，**静态编译定框架，动态调度挖性能**；数据流是受限动态调度的一类，场景化取舍，无绝对对错。

2. 调度效能取决于有效图与窗口的匹配，以及切块时**横向并行**与**纵向局部性**的平衡；要吃窗内动态调度的红利，工作须喂进窗口。

3. 手写与编译器互补地构造大图；数据流本质仍是**软件负重、硬件解放**，形态可以多样，无万能银弹。

4. 超节点演进下，系统成败还看集群能否组织单片能力：单片是入场券，通信、存储与分布式 Infra 常定出口上限——**不是「片内博弈已结束」**，而是单片与集群要一起设计。
