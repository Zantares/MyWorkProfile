# AI 芯片动态调度与数据流架构随笔

## 一、动态调度与数据流：一体两面

**动态调度**指运行时根据依赖与资源空闲决定何时发射。数据流是其中一类——**带编译期约束的受限动态调度**。

1. **广义动态调度（常以乱序执行为代表）**

乱序执行是其在 CPU 流水线中的经典实现：编译器输出线性指令流，**不固定拓扑、不做资源绑定**；硬件靠重命名、记分牌、乱序窗口处理未知依赖、分支与不规则访存。通用性强，但调度逻辑面积、功耗与延迟高。

2. **AI 数据流（受限动态调度）**

编译期定骨架，运行时轻量触发：

- 编译期：固化拓扑、通路、PE 映射；
- 运行时：在骨架内就绪触发、负载均衡、消气泡。

内部并不统一：有的几乎排死时间表，有的保留令牌就绪；共同点是**强编译约束**，差别在运行时机动空间。

3. **一体两面**

> 数据流 = 静态编译框架 + 受限动态调度  
> 乱序一类 = 弱拓扑约束 + 高自由度、高开销动态调度

二者是场景化取舍：数据流用软件复杂度换密度与能效；广义乱序用硬件开销换通用性。

两者都依赖调度，因而都碰到：**调度器一次能看见、能挖的有效计算图有多大？**

## 二、调度窗口与计算图大小

调度窗口指一次处于「可调度 / 在途」的**指令或 op** 范围（有别于 shared mem / 显存等存储上限），深度多在微架构或编译器内部，开发者不易直接看见。有效图宜落在窗口能吃饱、软硬件又扛得住的区间。

### 1. 图太小：并发度不够

细粒度小算子 launch 下，核内仍可调度，但**跨算子**并行与流水不足；依赖链被切开时更明显。数据流路线多靠编译器做大子图再映射。放大有效域的手段可互补：

| 手段 | 作用 | 局限 |
|---|---|---|
| **融合 / 子图放大** | 多 op 进入同一调度域 | 实现难；过大可能超窗 |
| **CUDA Graphs 等** | 一次提交多节点，利于无依赖重叠 | 不等于更大的 op 级调度窗 |
| **PDL 等依赖核重叠** | 压依赖边界气泡、提高 prefetch | 域仍碎；有硬件代数边界 |

### 2. 图太大：编译可得，窗口会超

整图或近整图可以编译，但时间、依赖分析、动态 shape、增量更新成本高。若要求海量 op **同时**待在窗口里，就绪与在途状态会胀。超窗后常见处理（可组合）：

| 手段 | 做法 | 要点 |
|---|---|---|
| **一次装得下就装** | 融合域 op 数 ≤ 窗口 | 域够小时最省事 |
| **静态切块 / 换配置** | 按窗口预算切开，块间同步再装下一块 | AI 加速器上常见；换 PE 映射时重于插 sync |
| **同流内屏障分期** | 长流中插 sync，排空后再进下一批 | 不必重新 launch；跨屏障无法再同窗调度；多为编译期插入 |
| **滑动窗口** | 完成后滑、新 op 连续准入 | CPU 乱序经典做法；AI 上较少作全图主路径 |

同构长流、不必重映射时，插 sync 往往够用；要换空间配置时，更接近静态切块。

### 3. 合适大小

太小则调度挖不满；太大则切块、屏障或滑窗都会在边界上付出并行与局部性代价。常见做法是融合做大，再按预算切开或分期，使**窗口能吃饱、边界可控**。

若必须切块或分期，边界如何画——横向挖并行，纵向保局部性？

## 三、切块中的横向并行与纵向局部性

切块不能只看数据依赖，还须权衡并行收益与访存损失。

1. **横向划分（并行维度）**

把**无依赖、可并行**的算子聚到同一 BB，增大窗内可挖的并发。多 Stream / CUDA Graphs 等外层重叠属于粗粒度软件调度；窗内动态调度只作用于**窗口可见的指令/op**。横向打包是为了**喂窗**。超窗或资源紧时仍可用外层手段，但要吃动态调度红利，工作须进窗。

2. **纵向划分（快存局部性维度）**

**链式依赖、共享片上 SRAM** 的串行算子宜同块或邻块。若只按「无依赖」拆散链条，中间结果易下刷 DDR，放大访存代价。

> **并行挖掘优先，存储局部性兜底**；memory-bound 时局部性往往更靠前。

这样的块由谁来构造——手写，还是编译器融合？

## 四、手写大图与编译器融合

两条路径都为撑起有效调度域。

1. **手写大算子**

把更多工作送进同一调度域，并在算法与访存结构上深挖。动态调度下，cycle 级手排时间表的红利变弱（发射由窗口按就绪决定）；仍常拉开差距的是算法、tiling 与多 stage / 双缓冲等显式结构。短板是成本高、难覆盖多模型；硬件或窗深一变，巨核要人肉重切。

2. **编译器融合**

自动聚合小算子，按窗口等预算融合与切分，换代和超窗时更易重来。短板是软件复杂（切分、映射、依赖、动态 shape）；指令排序上差距易缩小，热点算法与流水仍常落后专家核。

二者互补：热点手写，长尾与切分/换代靠编译。构图交给软件后，还要问：软件扛多少复杂度，硬件换回多少能效与密度？

## 五、无银弹：软件与硬件的分工

更深一层是：**用软件复杂度换硬件能效与算力密度**。

1. **数据流一侧**

拓扑、图优化、资源规划进编译期，硬件可少做通用乱序与大窗口记分牌，晶体管更多给计算与片上缓存，密度和能效往往更好做。

2. **适用边界**

更适配规整、可静态或半静态编译的 AI 负载；面对随机分支、未知依赖、不规则计算，广义动态调度（乱序）更灵活。

3. **小结**

场景化取舍，而非单一赢家：

- 通用计算：高自由度乱序通常更合适；
- 规整张量类 AI：**强编译约束 + 受限运行时**通常更划算，落地表可以是数据流、SIMT + 融合编译、偏确定性时间表等。

单片路径从调度、喂图、构图，落到按场景的软硬件分工，为的是把单片能力尽量打满。系统能否成立，还取决于**集群如何组织这些单片能力**，以及单片在集群中扮演什么角色。

## 六、开放讨论：超节点时代的单片能力与集群能力

开放问题是：单片能力**怎样被集群组织起来，又有多少能落到系统出口？**

### 1. 集群在难什么

大规模训练/推理的卡点常在：

- 多级存储（KV Cache、权重与激活分层）；
- 片间 / 节点间带宽与集合通信；
- 张量、流水、专家并行下的均衡与气泡。

单片利用率高，仍可能被跨卡等待、缓存不足或通信拖住，系统层往往更重。

### 2. 单片能力在集群里扮演什么

TP/PP/EP 与通信插入会打碎片内融合与切块，使窗内调度红利在出口被稀释，故单片最优不必等于系统最优。单片角色可拆开看：

- **入场券**：密度、能效、片上带宽与单卡效率，仍划成本与时延下限（推理尤甚）；
- **可被组织的硬件**：HBM、片间互联、同步与集合通信原语，是集群底座；
- **易被稀释的部分**：仅做窗内发射与局部融合，而上层切图与通信很粗时，出口上可能看不见。

关键在**层间接口**：并行策略如何少打碎局部性，硬件暴露何种同步与带宽，使集群吃得到单片。

### 3. 产业把「域」做大

近两年超节点叙事多是：**做大 Scale-up 域，再在域间 Scale-out**。华为灵衢（UnifiedBus）强调总线级互联、协议归一与池化，使多机逻辑上更像一台；平头哥真武配合 ICN 等做超节点，突出统一编址 / 内存语义与域内高带宽低时延，再经网络扩展。这是把「有效执行域」从单芯片延伸到紧耦合多卡，与「域太碎则调度与流水吃亏」同类，只是抬到机柜与集群。

### 4. 收束

单片打满是必要基础；通信、存储与分布式 Infra 往往划出集群出口上限；二者相连。仍可追问：并行切割下如何保住局部性？硬件与协议如何让「多卡像一域」付得起代价？

## 简要回顾

1. 动态调度与数据流一体两面：静态定框架，动态挖性能；场景化取舍。
2. 效能取决于有效图与窗口匹配，以及横向并行与纵向局部性；吃窗内红利须喂窗。
3. 手写与编译器互补构图；软件负重、硬件解放，形态多样。
4. 超节点下，单片是入场券，通信、存储与 Infra 常定出口上限；单片与集群宜一起设计。
