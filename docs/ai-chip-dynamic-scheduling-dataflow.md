# AI芯片动态调度与数据流架构 完整深度总结（含大模型超节点演进趋势）

## 一、核心定性：动态调度与数据流并非对立，而是一体两面

这是本次讨论最核心的底层认知，破除行业常见误区：

1. **广义动态调度（常以乱序执行为代表）**

动态调度是上位概念：运行时根据依赖与资源空闲决定何时发射。乱序执行是其在 CPU 指令流水线中的经典实现——完全依赖硬件兜底，编译器只输出线性指令流，**不固定任何计算拓扑、不做资源绑定**。硬件通过重命名、记分牌、乱序窗口，实时处理未知依赖、随机分支、不规则访存。

优势是**极致通用**，劣势是调度硬件面积、功耗、延迟极高，大量晶体管消耗在“调度逻辑”而非计算。

2. **AI数据流架构（受限动态调度）**

数据流**没有抛弃动态调度**，而是做了**编译期约束、硬件减负**：

- 编译期：提前固化全局计算图拓扑、通路、PE映射，搭建静态执行骨架；

- 运行时：硬件保留**轻量动态调度**，依靠数据令牌就绪机制，在固定拓扑内自动触发执行、均衡负载、消除空闲气泡。

「数据流」内部也并不统一：有的几乎全靠编译期排程（如偏确定性时间表的设计），有的在固定拓扑里保留轻量就绪触发；共同点是**强编译约束**，差别只在运行时还能「见机行事」多少。

3. **二者真实关系**

数据流 = **静态编译框架 \+ 受限高效动态调度**

广义动态调度（乱序执行） = **弱拓扑约束 \+ 全自由度高开销动态调度**

二者不是优劣对立，是**场景化取舍**：数据流用软件复杂度，换取硬件极致算力密度与能效；广义动态调度用硬件高开销，换取极致通用性。

> 误区解释：推崇全乱序、否定数据流的观点，本质是**用通用计算的评价标准，评判AI专用架构**。通用负载下数据流受限，AI规整负载下数据流架构碾压通用乱序，无绝对对错。

## 二、调度性能关键：调度窗口与计算图尺寸的精准匹配

调度器能挖出多少跨算子并行，很大程度取决于**有效计算图如何进入有限的调度窗口**。图不是越小越好，也不是越大越好；工程上常见的是在几种模式之间折中，而不是存在唯一最优解。

先把对象说清：这里的**调度窗口**约束的是**指令（或泛化为图上的 op / 节点）**——一次能处于「可调度 / 在途」的条数或范围。它和 SRAM、显存、shared memory 等**存储类资源**不是一回事：后者编译期常对开发者暴露（上限、占用率、OOM）；窗口深度多半只活在 CPU 微架构或厂商编译器的 machine model 里，**算子 / 框架开发者很难直接感知**，超窗也很少变成一条清晰报错，更多是默默再切段或利用率变差。窗里活着的 op 多，间接会顶到存储，但讨论窗口时不要用 spill / OOM 代替超窗本身。

1. **过小图（常见多算子细粒度 launch / 逐算子加载）**

问题不在 host 提交贵，而在**可见的有效调度域过小**。每次只提交或装入单个小算子时，核内（如 GPU 的 warp/SM）仍可动态调度，但**跨算子**的依赖掩盖、负载均衡与流水并发挖不足——动态调度并非失灵，而是窗口里没有足够的跨算子工作可挖。

真痛点更常出在**依赖链**被切开：无依赖多核用多 Stream 等重叠往往已能吃饱；有依赖时，边界气泡变大。GPU 上的「一次可见工作集」与数据流芯片上的「硬件调度窗口」机制不同，但是**同构问题**：有效图太碎，跨算子并行与流水就上不去。

数据流芯片通常更依赖编译器把子图做「够大」再映射，而不是 eager 式小图 launch；块内才用数据流挖并行。缓解路径可以分层看，且**常常叠用**：

| 路径 | 做法 | 优点 | 局限 |
|---|---|---|---|
| **子图放大 / 融合** | 多算子进入**同一执行调度域** | 治本：窗里（或一次映射里）有足够 op 可挖 | 融合难；域变大后仍要面对「有限窗怎么吃」；谁来融见后文 |
| **CUDA Graphs 等** | 一次提交多节点，改善运行时可见性与**无依赖**核重叠 | 提交整洁，独立算子易并发 | 不替代融合；也不等于拥有更大的指令/op 级调度窗 |
| **PDL 等跨核依赖重叠** | 后继核提前 prefetch，与前驱尾部重叠 | 不融合也能压依赖边界气泡 | 治标；域仍碎；有架构/场景边界 |

2. **整图 / 大图：可做，但成本高**

把整张（或近整张）模型图编译出来是**可以做的**；难点在复杂度与维护（编译时间、依赖分析、动态 shape、增量更新等）。若再要求硬件**同时**把海量 op 暴露在超大调度窗口里，就绪逻辑与在途状态会跟着胀。

更准确的说法：**整图编译可行，代价高；无约束的超大窗口更贵。** 这与「显存够不够」是不同层的问题。

3. **有限窗口怎么吃大图（非唯一最优）**

图已经够大之后，窗口仍然有限。关键区分：**不一定要退回 host 重新切图再 launch**——同一次执行流里也可以换窗。

| 模式 | 做法 | 要点 |
|---|---|---|
| **A. 一次装入** | 融合后区域的 op 数 ≤ 窗口，整段进入再调度 | 最简单；域足够小时成立 |
| **B. 静态切块 + 换配置 / 再装载** | 编译器按内部窗口类预算切开；装块₁ → 块内动态调度 → 同步并**换配置/换块** → 装块₂ … | AI 加速器上常见。切在**软件（编译器）**，对齐的是未对算子作者公开的 machine model。若下一块还需不同 PE 映射，往往重于一条 sync |
| **B′. 同执行流内屏障分期** | 仍是一次 launch / 一条长流；在超窗处（多为编译期）**插入 sync / 屏障**，排空在途 op 后再让下一批进窗 | **不必重新切图 launch**。代价是屏障两侧不能再一起被动态调度，跨代并行会丢。少见「硬件检测到超窗再自动插 sync」；多为编译器事先插好 |
| **C. 滑动窗口** | 发射/完成后窗口后滑，新 op **连续准入**，不必整窗排空 | 与 CPU 乱序「有限指令窗 + 窗内动态发射 + 向前推进」是**经典搭配**。多候选准入/发射时变成动态滑窗 + 动态发射，更复杂。当代 AI 加速器较少以全图滑窗为主路径 |

关系上：B′ 比 B 轻（同流内分代），比 C 粗（硬屏障 vs 边退边进）。选 B **不会**自动变成 C；只有在块边界还做细粒度重叠时才向滑窗靠。超窗时「插 sync 即可」在**同构长流、不必重映射**的前提下成立；需要换空间映射时，仍更接近 B。

实务里常见：**能装下走 A**；否则由编译器做 B 或 B′；Graphs / PDL 补跨核层；C 作对照极。对开发者而言，这些多半不透明——感知到的是慢或工具里的时间线，而不是「超出调度窗口」。

若走必须切块 / 分期的路径（B / B′），下一块问题就是：**边界画在哪**——既要横向挖并行，又要纵向保住数据局部性（后者常牵动存储，但动机仍从调度域边界谈起）。

## 三、核心工程权衡：计算图的横向并行 \& 纵向存储局部性切块策略

AI芯片图切块**不能单一依赖数据依赖**，必须做双向权衡，解决“并行收益”和“访存损失”的核心矛盾：

1. **横向划分（并行维度）**

优先将**无数据依赖、可并行执行**的算子聚合为同一BB子图块，最大化块内动态调度的乱序并发能力，充分释放硬件并行算力。

2. **纵向划分（快存局部性维度）**

不能单纯拆分串行依赖算子：**存在链式数据依赖、共享片上SRAM/快存**的串行算子，必须保留在同块或相邻块。

- 错误做法：仅按“无依赖打包”，拆分串行链式算子；

- 致命后果：中间结果无法驻留片上快存，被迫下刷DDR慢内存，带来毁灭性访存延迟与带宽损失。

> 最终切块原则：**并行挖掘优先，存储局部性兜底**，在调度并发收益和访存开销之间取最优平衡点。

## 四、实现路径对比：手写算子大图 VS 编译器自动融合

两种方案目标完全一致：**构建足够大的有效调度域，支撑动态调度发挥极致性能**

1. **手写大算子（人工构图）**

人工搭建超大计算区域，调度窗口充足，能100%吃满动态调度能力，性能极致、无编译损耗；

短板是开发成本极高、迭代慢、无法适配海量模型，不具备通用性。

2. **编译器自动算子融合（编译构图）**

通过编译优化自动聚合小算子、生成标准子图簇，自动适配硬件窗口、平衡并行与局部性；

短板是**编译器软件复杂度极高**，需要解决图切分、资源映射、依赖分析、动态Shape适配等大量难题。

## 五、架构终极取舍：无银弹，软件换硬件算力上限

所有AI架构的底层逻辑统一：**用软件复杂度置换硬件能效上限**

1. **数据流架构核心优势**

将复杂的拓扑编排、图优化、资源规划全部压入编译期，大幅简化硬件逻辑；

硬件无需昂贵的通用乱序、重命名、大窗口记分牌，**节省的晶体管全部用于计算单元、片上缓存**，实现同工艺下极致的算力密度与能效。

2. **架构固有边界**

仅适配**规整、可静态编译的AI负载**；面对通用随机分支、未知动态依赖、不规则计算，灵活性远不如CPU全乱序架构。

3. **核心结论**

动态调度与数据流的博弈**没有绝对赢家**，是典型的场景化工程取舍：

- 通用计算：全乱序动态调度更优；

- AI训练/推理：数据流受限动态调度是最优解。

## 六、产业高阶升华：大模型超节点时代，算力调度不再是核心瓶颈

单芯片微架构的所有优化（动态调度、数据流、算子融合），**在超节点分布式系统面前，优先级大幅降级**，这是当前行业最关键的演进趋势：

### 1\. 单芯片优化的收益已被系统瓶颈掩盖

无论单芯片调度设计多么完美、算力利用率多么极致，大模型超节点的真正瓶颈**不在片内计算**，而在：

- 多级存储体系（KV Cache、权重缓存、片上/片外存储分层）；

- 芯片/节点间通信带宽、集合通信延迟；

- 分布式数据吞吐与负载均衡。

单芯片100%算力利用率，无法弥补跨卡通信阻塞、KV Cache溢出、带宽不足带来的系统卡顿，**局部架构优化无法解决全局系统瓶颈**。

### 2\. 系统层约束反向绑架芯片编译逻辑

单芯片最优的图融合、切块、调度策略，经常会被**分布式张量分片、流水线并行、通信插入**打碎。

片内精心优化的动态调度收益，会因为上层分布式调度、通信同步被稀释，**软件Infra的优先级高于单芯片微架构**。

### 3\. 大模型时代的真正核心：带宽、存储、通信、分布式Infra

超节点竞争力的决定性因素：

1. **硬件层**：层级存储设计、片间/节点间通信带宽、访存吞吐；

2. **软件层**：分布式调度器、KV Cache管理、内存池、集合通信库、并行策略Infra。

### 4\. 最终层级结论

1. **底层基础**：动态调度、数据流架构、算子融合（单芯片算力利用率，必要非充分条件）；

2. **顶层上限**：存储、带宽、跨芯通信、分布式软件基础设施（超节点整体性能的决定性条件）。

## 全文终极总结

1. 动态调度与数据流一体两面，**静态编译定框架，动态调度挖性能**，是AI专用架构最优取舍；

2. 调度性能取决于计算图切块策略，必须平衡**横向并行度**与**纵向存储局部性**；

3. 数据流本质是**软件负重、硬件解放**，牺牲编译通用性换取AI算力能效，无万能银弹；

4. 大模型超节点演进下，**单芯片架构博弈已内卷完毕**，未来核心竞争从“怎么算得快”转向“怎么传得快、存得下、调度得好”，通信、存储、分布式软件Infra才是行业终局瓶颈。
